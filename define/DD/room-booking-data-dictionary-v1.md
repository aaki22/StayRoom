# Room Booking — Data Dictionary v1.0

Based on API contract v0.3. PostgreSQL with PostGIS. This document defines storage for hotel discovery, one-room reservations, Razorpay Test Mode payments, refunds and administration.

## Conventions

- Database columns use snake_case; API fields use camelCase except the agreed response envelope.
- IDs are UUID primary keys generated by the application or database. Provider IDs remain strings.
- Timestamps use TIMESTAMPTZ and are returned in UTC. Stay dates use DATE in the hotel timezone, Asia/Kolkata.
- Amounts use BIGINT in INR paise; ₹2,500 = 250000. Serialize safely as JSON numbers within JavaScript safe integer bounds; validate upper limits before arithmetic.
- Required means NOT NULL; nullable fields are explicitly marked. All foreign keys use ON DELETE RESTRICT unless otherwise stated. No hard-delete API in v1.
- Enum values below are enforced with CHECK constraints or PostgreSQL enums. Database defaults never replace request validation.
- Every mutable business table has created_at and updated_at TIMESTAMPTZ NOT NULL DEFAULT now(); update updated_at on every mutation. Tables explicitly marked immutable have created_at only.
- PK = primary key; FK = foreign key; UQ = unique; NN = NOT NULL. Empty arrays are allowed for amenities and images.

## Booking lifecycle

| Current | Allowed next states | Trigger |
|---|---|---|
| PENDING_PAYMENT | CONFIRMED, CANCELLED, EXPIRED | Verified capture while valid, cancellation, or hold timeout |
| CONFIRMED | CANCELLED, CHECKED_IN, NO_SHOW | Allowed cancellation, arrival, or missed stay |
| CHECKED_IN | CHECKED_OUT | Admin checkout |
| CANCELLED, EXPIRED, CHECKED_OUT, NO_SHOW | None | Terminal reservation states |

Payment state is separate: a late captured payment can coexist with EXPIRED while its refund is PENDING. Only accepted captured payment sets booking payment_status=PAID. Late captures on unpaid expired/cancelled bookings set REFUND_PENDING and subsequent refund state. A failed attempt does not change PENDING_PAYMENT to a terminal state.

## Prevent overlapping reservations

Enable PostgreSQL btree_gist. Add an exclusion constraint on bookings using GiST: room_id WITH = and stay_period WITH &&, restricted to status IN (PENDING_PAYMENT, CONFIRMED, CHECKED_IN). Adjacent stays do not overlap because stay_period uses [).

Do not put now() in an index predicate to filter expired holds. Before allocating a room, lock its row, mark expired PENDING_PAYMENT bookings EXPIRED and clear their hold timestamp, then attempt allocation under the exclusion constraint. A scheduled expiry worker does the same cleanup. Lock the booking when confirming/cancelling/expiring so late payments cannot revive released inventory. Refresh room/hotel/type eligibility inside the allocation transaction; inventory maintenance and price edits must use compatible locks. Lock order: hotel → room type → room → booking → payment/order/refund rows. Workers must use the same order when touching those resources. Retry bounded deadlock/serialization failures.

Expired holds may remain physically indexed until cleaned; discovery explicitly excludes holds whose expiry has passed. Allocation performs cleanup before inserting. Confirmation after expiry enqueues a refund even when the provider capture time was earlier. This is the conservative payment policy agreed in the API.

## Location search

Store point as ST_SetSRID(ST_MakePoint(longitude, latitude), 4326)::geography. Input latitude is -90..90, longitude -180..180. Search within radiusKm × 1000 metres using ST_DWithin, compute ST_Distance for sorting and return kilometres rounded for display. Geography provides straight-line surface distance, not route distance. City search uses case-insensitive matching and returns distanceKm=null. Customer search coordinates are request parameters, not user profile fields; no location-history table is needed.

## Validation and operational boundaries

- Enforce date horizon (365 days), local today, same-day check-in cutoff and current capacity in transactional application logic. These depend on time/related rows and are not simple immutable CHECK constraints. CHECK constraints enforce intrinsic dates, ranges and arithmetic.
- Payment/order/refund amount and currency must match linked records under transaction; a basic FK alone cannot enforce these cross-table rules.
- Send reset email through a configured mail adapter. If reliable asynchronous delivery is required, add an email outbox later; do not treat a missing email delivery as a successful account recovery.
- Workers use durable rows for payment-order reconciliation, refund retries and webhook processing. Claim with row locks/leases, recover abandoned work and surface exhausted failures to admins.
- Configure gateway keys outside the database. Test-mode orders cannot become live transactions by changing a database field.
- Availability is not a reservation. Only booking allocation creates a hold. No quote table or endpoint exists.
- Full refunds only in v1. Partial refunds, multiple rooms per booking, dynamic pricing, coupons, hotel-owner accounts and real-money payment are outside this dictionary.
